# Contributing

Thanks for taking the time. Issues and pull requests are both welcome.

## Opening an issue

The fastest way to help is an issue. Pick the template that fits (bug report or
feature request) and fill in the version and reproduction steps. A bug I can
reproduce gets fixed; one I cannot usually stalls.

## Opening a pull request

You do not need write access. Fork the repo, branch off `main`, push to your
fork, and open a pull request back to `main`. I review and merge.

Before you open it:

1. Build and test the project. Every repo documents its commands in the README,
   usually under a "Development" heading. If yours does not, say so in the PR and
   I will add it.
2. Keep the change focused. One idea per pull request reviews faster than a
   sweep, and it survives review even if one part is rejected.
3. Match the surrounding code. Style rules that matter are enforced by the
   project's own linter or formatter, not by preference.

Leave versions, changelogs, and release tags alone. I cut releases, and a PR
that bumps a version conflicts with the next one that does the same.

## Behaviour

The [Code of Conduct](CODE_OF_CONDUCT.md) applies to issues, pull requests, and
discussions.

## Security

Do not report vulnerabilities in a public issue. The
[security policy](SECURITY.md) explains where to send them.
